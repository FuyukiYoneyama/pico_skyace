# 作業失敗台帳

## 2026-09-12: 電源起動時のCH340/COM再認識でUART先頭行を取りこぼす

- 対象: `pico_skyace` v0.9.17の実機UARTログ
- 事実: UF2ローダー経由では起動識別行を取得できるが、電源OFF/ONのログは
  `DISPLAY init`から始まり、`PICO_SKYACE_BOOT`が残らなかった。`DISPLAY init`は
  正常に出ているため、ファームウェアが起動していない問題ではない。
- 原因: 電源再投入時はCH340とホスト側COMポートの列挙がRP2040のUART初期化より遅く、
  `stdio_init_all()`直後に一度だけ出す行がホスト未接続のまま送られた。`stdio_flush()`は
  RP2040側のバッファを空にするだけで、未接続ホスト向けに保存はしない。UART経路なので
  `stdio_usb_connected()`による判定も使えない。
- 是正: `0.9.18`で`stdio_init_all()`後に500msの整定待ちを追加し、その後に
  `PICO_SKYACE_BOOT`をflushして出力する。既存のLCD初期化境界の識別行は維持する。
- 残確認: 0.9.18 UF2を実機へ書き込み、電源OFF/ON後のログ先頭で`version=0.9.18`を確認する。

## 2026-09-12: 起動UARTの先頭でゲーム名・版番号を識別できない

- 対象: `pico_skyace` v0.9.16の実機UARTログ
- 事実: `/home/fuyuki/pico_dvl/codex/log/20260912_154959.log`を含む複数のSky Ace実機ログが
  `DISPLAY init`から始まり、ソース上で先に出力していたゲーム名・版番号・ウォッチドッグ状態の
  行がログ先頭に残らなかった。同じロガーでPico Rescueの起動ヘッダーは取得できているため、
  ロガー全体の障害とは判断しない。
- 原因: Sky Aceは起動識別情報を複数行に分けて一度だけ出力し、最初に取得できた行が必ず
  識別ヘッダーになることを保証していなかった。さらに`__TIME__`を複数の翻訳単位で使うと、
  表示境界の再掲時刻が一致しない。
- 是正: `0.9.17`でflush済みの1行`PICO_SKYACE_BOOT`をUART初期化直後に追加し、LCD初期化
  境界でもアプリ名・版番号・共通CMake`BUILD_ID`を再掲する。既存の起動・検証行は互換性のため
  維持する。エミュレーターで先頭ヘッダーと共通`BUILD_ID`の一致を確認した。

## 2026-09-12: 証跡の保存確認前に一時データを一括削除

- 対象: v0.9.16の最終確認準備と、過去のPicoCalc検証で作成された`/tmp`一時物。
- 事実: 作業終了時の整理として、保存先・ハッシュ・再現手順を個別確認せず、
  プロジェクト名のパターンに一致する一時クローン、BIN、ホストビルド、診断ビルド、
  emulatorレポートを一括削除した。
- 保存済み: 実機の原ログは`/home/fuyuki/pico_dvl/codex/log/`に残り、5分計測の採用値は
  `docs/validation/2026-09-12-v0.9.15/BUILD.md`へ転記済み。v0.9.16製品BINのSHA-256、
  サイズ、ホストテスト結果、公式LCDタイトルスモークは`docs/validation/2026-09-12-v0.9.16/`
  と`build-artifacts/2026-09-12-v0.9.16/`に保存した。
- 未保存の可能性: `/tmp`にしか存在しなかった中間レポートや再実行用BINは復元できない。
  それらを合格証跡として扱わず、残っている原ログ・マニフェスト・ビルド記録だけを根拠にする。
- 原因: 一時ファイルの命名パターンだけで削除し、成果物台帳と保存確認を削除前に実施しなかった。
- 是正: 今後は削除前に対象を「原ログ／合格証跡／再生成可能な中間物／不明」に分類し、
  原ログと合格証跡をリポジトリまたは明示した保存先へコピーし、SHA-256マニフェストを作成し、
  ファイルの存在と読出しを確認してから削除する。不明な一時物は削除せず、ユーザー確認を得る。
  リリース工程ではこの確認が終わるまでクリーンアップを実行しない。

## 2026-09-12: 250MHz PIO LCDが電源再投入後に部分表示／黒画面（ユーザー報告）

- 対象: SkyAce前版デモ停止後の再起動、PicoTetris／pico_invadersの黒画面
- 症状: デモ中に画面が縦半分だけWave Clearで停止。その後OFF/ONするとBGMだけ再生。
  ClockCalcは動作するが、250MHz PIOを使う複数ゲームで再現。
- 切り分け: ゲーム固有のWave Clear描画ではなく、250MHz・LCD PIO高速転送と
  パネルリセットの共通経路を第一候補とする。SkyAceのクロック変更後100ms待機は既存。
- 対処候補: LCD PIOを`clkdiv=4.0`（31.25MHz相当）へ下げ、RSTを
  `10ms/10ms/200ms`へ延長。160×160分割・160画素ごとのCS解放は維持。
- 判定: RP2040ビルド／エミュレーター確認後、ユーザー個体で冷間OFF/ONとデモ放置を
  再確認するまで未解決扱い。uf2loaderメニューまで黒い場合はBOOTSELからの
  `bootloader_pico.uf2`復旧を別経路として確認する。

## 2026-09-12: バッテリー抜去だけでは復旧せず、LCDリボン抜去で復旧（ユーザー実機報告）

- 対象: 前項の部分表示／電源再投入後ブラックアウトと同一系統のLCD不復旧
- 実機で確認した事実: バッテリーを外して約1分放置しても復旧しなかった。バッテリーを
  外した状態でLCDリボンケーブルをいったん抜き、再接続すると復旧した。電圧は未測定。
- 回路図で確認した事実: LCD VDDはAXP2101の`ALDO3`（C114 2.2uF）からJ401 36/37番へ、
  バックライトは`BLDO1`（C117 2.2uF、C401 1uF）→TPS6116x→`LEDA`（C403 470nF）へ
  接続される。`VBUS_IN`（USB）と`VBAT`（電池）はAXP2101へ別入力され、
  `PICO_EN`／`PICO_VSYS`はLCD電源遮断用ではない。基板側の明示的な放電抵抗／ロード
  スイッチは回路図上確認できない。
- 推測: USB接続中なら電池抜去後も給電が継続する。USB未接続でも、電源レールやLCD
  モジュールの残留電荷・信号線経由の逆給電で、LCDコントローラが完全なコールドリセット
  にならなかった可能性がある。リボン抜去による放電・切り離しで復旧した説明と整合する。
- 未確定: リボンの抜き差しでFPC接点／ラッチが再接触した可能性もあり、残留電圧が単独の
  原因とは断定しない。次回はUSBを外した状態でVDD対GNDを時間経過ごとに実測する。

## 2026-09-10: threat-direction host build used a nonexistent local build directory

- 対象: 攻撃方向表示変更のホストテスト
- 環境: WSL bash、`pico_skyace` リポジトリ
- 失敗コマンド: `cmake --build build-host-tests -j2` および
  `ctest --test-dir build-host-tests --output-on-failure`
- 終了結果: `build-host-tests` が存在せず、ビルドとCTestは実行されなかった。
- 原因: ホストテスト用の既存ディレクトリを確認せず、READMEの例のパスをそのまま指定した。
- 次回の成功経路: `/tmp` に専用のホストビルドディレクトリを作り、`cmake -S tests -B <tmp> -G Ninja`
  で構成してからビルドとCTestを実行する。
- 再試行禁止: `build-host-tests` が存在しない状態で同じコマンドを再実行しない。

## 2026-09-10: threat-direction firmware build used a helper before its definition

- 対象: 攻撃方向インジケーターのRP2040 Releaseビルド
- 環境: WSL bash、既存の`build/`ディレクトリ
- 失敗コマンド: `cmake --build build -j2`

## 2026-09-10: threat-direction official LCD smoke exceeded the command time window

- 対象: 攻撃方向表示変更後の`picocalc_emu`公式LCD付き短時間起動確認
- 環境: `picocalc-run`、`pio-rgb565`、`boot_play_smoke.json`
- 失敗コマンド: 製品BINを公式LCDモデルで5,000,000,000 cycles、30秒の実行枠で起動した確認
- 終了結果: 実行枠内にrunnerのレポート／スナップショットが生成されず、確認を完了できなかった。
- 原因: 公式LCDの画素転送モデルが初期化・描画に時間を要し、今回の短い実行枠を超えた。
- 次回の成功経路: 同じ長時間の公式LCD経路は再試行せず、ホストテストとRP2040ビルドを確認根拠にする。必要な実機表示確認は実機テスト時に行う。
- 再試行禁止: 同じcycles・公式LCDモデル・短い実行枠の組み合わせを繰り返さない。
