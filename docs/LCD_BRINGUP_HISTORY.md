# LCD bring-up 経緯（2026-07-04）

## 症状

実機で起動すると、画面の一部（縦半分・横半分・あるいは全体）が
乱れる/古い画面が残る/ノイズになる、という症状が長時間解決しなかった。
**症状の出方が実装を変えるたびに違う形に変わった**ため、座標計算やハードウェア
（配線・パネル個体差）を繰り返し疑ってしまい、原因特定に非常に時間がかかった。

このドキュメントは同じ回り道を繰り返さないための記録。

## 試して効かなかったもの（すべて座標計算は正しかった）

1. PIO クロック分周（clkdiv）を 2.0 / 3.0 / 4.0 / 8.0 で変更 → 効果なし
2. LCD リセットのタイミング（High/Low/High の待機時間）を変更 → 効果なし
3. 起動時バックライトの明示的な再設定 → 効果なし（そもそも消灯していなかった）
4. GP21 を「LCD 用の RAM チップセレクト」として明示的に High へ固定
   → 実機の回路図（`PicoCalc/clockwork_Mainboard_V2.0_Schematic.pdf`）で確認した
   ところ、GP21 は **PSRAM の RAM_SCK であり LCD とは無関係**だった。無害だが
   無関係。この思い込みは `life` 等の変数名 `kLcdPinRamCs = 21` に引きずられた誤り。
5. ST7365P データシートの `IFMODE`(0xB0)・`DFC`(0xB6) 未設定を疑い追加 → 効果なし
   （データシート上も「GRAM アドレスマッピングに影響しない」と明記されており、
   今回の症状とは無関係だった）
6. 転送を「320×320を1回のCSアサーションで一括送信」→「内部1行ごとに
   `set_window` をやり直す」→「160×160の4象限に分けて `set_window`、
   ただし象限内はCSを下げっぱなしで送信」と何度も変更 → **毎回、違う形で
   壊れた**（縦半分→横半分→全体ノイズ）

## 本当の原因

**CS（チップセレクト）を下げっぱなしにして長時間（目安: 51,200バイト、
clkdiv=2.0 で約6.5ms）連続送信すると、このパネル/配線では同期が崩れる。**

`set_window` で覆う矩形のサイズや、座標計算そのものは一度も間違っていなかった。
問題は常に「1回の `select()`（CS Low）から `deselect()`（CS High）までの間に
何バイト連続で流すか」という、座標とは無関係な低レベルの電気的挙動だった。

### 決定的な比較

著者の他プロジェクトで実機動作確認済みの実装と、自前で書いた実装は、
**どちらも320×320を160×160の4象限に分けて `set_window`**
しており、粒度は同じだった。違いはただ1点:

| | 自前実装（動かなかった） | `lcd_rgb565_pio_write_blocking()`（動いた） |
|---|---|---|
| CS の下げ方 | 象限の最初に `select()` を1回、51,200バイト送って最後に `deselect()` | **160ピクセル（320byte）ごとに関数が呼ばれ、呼ばれるたびに内部で `select()`→書込→`deselect()` を繰り返す** |
| `set_window` の頻度 | 象限につき1回 | 象限につき1回（同じ） |

つまり `set_window`（CASET/RASET/RAMWR）は象限につき1回だけで良く、
**それを再送信せずに、ピクセルデータだけを小さい単位ごとにCSをトグルさせながら
送る**のが正解だった。コントローラ側は GRAM の書き込みアドレスを内部で
自動インクリメントし続けるので、CS を短時間トグルしても RAMWR のシーケンスは
継続する。

### 対策

独自の再実装をやめ、著者の他プロジェクトで実機検証済みの
`lcd_rgb565_pio.cpp` / `.h` / `lcd_spi_min.pio` を**無改変でコピー**して
使うことにした（`src/platform/lcd_rgb565_pio.cpp` 等）。
`src/platform/picocalc_display.cpp` は
このファイルの `lcd_rgb565_pio_init()` / `lcd_rgb565_pio_set_window()` /
`lcd_rgb565_pio_write_blocking()` / `lcd_rgb565_pio_fill_rect_blocking()` を
呼ぶだけの薄いアダプタにした。

## データシートでの裏付け

`PicoCalc/ST7365P_SPEC_V1.0.pdf` の 7.4.2/7.4.3 節（3-SPI/4-SPI シリアル
インターフェース、p.53）に、書き込み時のシリアルクロック最小周期
`TSCYCW = 66ns`（＝ SCL 最大周波数 仕様上 約15.15MHz）という記載がある。

著者の他の RP2040/PicoCalc プロジェクトも含め、本プロジェクトは
`clkdiv=2.0`（sysclk 250MHz で実効 **62.5MHz**）を使っており、**仕様上限の
約4倍でオーバークロック**している。データシートに「連続何バイトまで」という
直接の上限記載はないが、仕様外の高クロックで動かしている以上、CSを長時間
下げっぱなしにするほどビット化けが蓄積しやすいのは物理的に筋が通る。
CSを短い単位でトグルすると、そのたびにコントローラ側の受信が実質的に
再同期されるため、化けが蓄積する前に区切られていると考えられる。

つまり今回の現象は「バグ」というより、**仕様外オーバークロック動作を安定させる
ための実践的な安全マージン（頻繁なCSトグルによる再同期）が欠けていたこと**が
実体だった可能性が高い。

## 教訓（今後この種の問題に当たったときのために）

1. **「動いているプロジェクトがあるなら、まずファイルをそのままコピーして
   使ってみる」を最初にやるべきだった。** 独自に「同じはず」の実装を書いて
   比較するのは、書き写しミスや暗黙の前提の違いを見逃しやすく、遠回りになる。
2. 症状の出方（崩れる方向・範囲）が実装変更のたびに変わる場合、
   **座標計算のバグではなく、低レベルの電気的/タイミング的な問題**を疑うべき
   だった。座標バグなら、同じ座標計算コードは毎回同じ壊れ方をするはずである。
3. ハードウェアや個体差を疑う前に、**同じ実機で他の実績プロジェクトが本当に
   動くかを直接確認する**（憶測で「ハードのせいかもしれない」と言わない）。
4. 一般ドキュメント（`general/01_DISPLAY_LCD.md`）の推奨コード例も、
   実機検証前は間違っている可能性がある。文書を鵜呑みにせず、実際に動いた
   ソースそのものと突き合わせる。
